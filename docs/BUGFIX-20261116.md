## 实证边界

`scripts/regression/f02-cleanup.mjs` 和 `f13-import.mjs` 使用 PGlite 加速 SQL 回归，不能替代真实 Supabase。`scripts/supabase-integration.mjs` 另行启动独立 Docker 项目，应用原三份及新增迁移，调用真实 Auth、PostgREST、Storage、Edge Functions；通过关闭 Storage 容器和数据库删除触发器注入失败，并在 finally 停止该隔离项目。它也调用真实同步代码检验 ID 映射、版本递增和媒体复用，再分别导出和构建 local/supabase 来源。不读取私有环境文件，不连接生产项目。

浏览器 UI 的 Mock 测试继续保留；CMS 故障场景精确限定为测试步骤内 5 次 TUS PATCH 500 和 1 次 note.save_draft 409，其他 HTTP/JS 错误均失败。明信片验收统计照片内部区域，资源验收执行实际 GLB/图片/HDR 解码及树冠遮罩校验。

依赖锁定的 `@supabase/supabase-js` / `auth-js` 2.119.0 声明 Node >=22，Vite 7.3.8 声明 Node ^20.19 或 >=22.12。原 CI/Pages 的 Node 20 与 Supabase 依赖要求不符，因此两条工作流统一为实际本机验收使用的 Node 24，项目 engines 调整为 >=22.12.0。

## 公开快照与 Pages

本仓库新增的 `site-content` 是显式空快照，避免把本机真实内容自动写入可提交目录。实际发布前在本机执行以下命令更新它，检查差异后自行提交：

```powershell
$env:LOCAL_CMS_DATA_DIR = '你的本地编辑数据目录'
npm run export:public -- --source local
$env:PAPER_HOME_FORCE_LOCAL = '1'
$env:PAPER_HOME_SNAPSHOT_DIR = (Resolve-Path site-content).Path
npm run build:local
```

云端导出只需要 `SUPABASE_URL` 和 `SUPABASE_ANON_KEY`（或对应 VITE 公开变量），不读取 `.env.local`、不用 service-role、不写远端内容：

```powershell
npm run export:public -- --source supabase --out '独立公开快照目录'
```

Pages 手动发布必须选择 `content_source=local|supabase`。local 读取已提交的 `site-content`；supabase 读取公开 URL/key，导出到运行器临时目录。`allow_sample_fallback=true` 现在表示明确启用本地演示分支，仅允许 local 来源；云端失败不会回退到本地或示例。两者均通过同一快照验证和 `build:local` 链路。私有 `local-data` 继续忽略。未自动提交、应用生产迁移或发布 Pages。

## 数据库发布顺序

1. 部署支持 `CMS_MEDIA_CLEANUP_ENABLED=0` 的函数并关闭清理，等待旧任务结束。
2. 应用新增增量迁移，再部署匹配版本的所有函数。
3. 验证领取、引用拒绝、文件删除及数据库确认、失败重试。
4. 移除暂停设置或设置为 `1` 后启用清理。缺失新 RPC 时新版函数拒绝执行文件删除。

已有异常素材不会被自动恢复为 ready；检查存储文件后另行修复。原有三个历史迁移保持不变。
